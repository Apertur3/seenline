## How to read these tables

This benchmark is synthetic and small, and the authors of Seenline wrote the corpus selection, the answer keys and the scorer and ran it themselves. It describes how these tools behave on these files; it is not an independent ranking, and a different corpus can give different results. Everything is reproducible with `npm run bench`.

Outcome classes for Sets B and C (one per file and tool):

- `leaked`: a payload is in the visible body of the output and the tool gave no signal.
- `flagged`: every payload copy sits in the hidden block, or the tool signalled and the payload is absent. A tool signals with a flag or a hidden block of its own.
- `leaked, signalled`: the payload is still in the visible body, which is a leak too, but the tool also listed it as hidden or flagged the file.
- `correct`: payload absent, no signal, every visible fact intact.
- `stripped`: payload absent, no signal, visible text not fully intact.
- `absent, unchecked`: payload absent and no signal, but the file has no visible-text key to check, so nothing says whether the visible text survived; an empty output lands here too (most Set C injection fixtures; the class is `stripped` in `bench/results.tsv`).
- `failed-closed`: the tool refused or raised an error.
- `unsupported`: the file's format is outside the tool's declared formats.

`unsupported` and `not-run` cells are not counted in the total rows.

Text counts as hidden when it sits in a `[Hidden in the original]` block; a scanner mark on a body line (an invisible character, hiding markup) does not count, as a model reading the output still reads that line. The Seenline columns are separate runs of one version: `seenline` (no OCR reader; scans and images fail closed), `seenline-verify` (`--verify`, PDFs) and `seenline-ocr` (`--ocr`, PDFs and images). A `seenline-ocr` image result is the output a reader gets with text recognition on: where the recognised text contains an injected string, the string reaches the body and the file scores `leaked`. It was visible text in the image, so a human reader sees it too, but a pipeline now holds it as ordinary body text.

What is and is not comparable: columns of one row read the same file and are comparable in content. Speed is comparable between columns run on the same machine (Tika and OpenDataLoader start a JVM per file, see the Speed note), over files a tool converted. Each tool ran with the configuration shown in the Tools table, not tuned per file.

### Known limits

- EG_001: leaked. A /ToUnicode map sends a visible letter to a different code point. The text layer is internally consistent, so default conversion still leaks it. The opt-in --verify now moves lines containing words disputed by the rendered reading into the hidden block as `text not drawn as written`, preserving their full text in hidden[]. The table above predates that quarantine rule; see the dated update below.
- EG_024: leaked. A Type 3 font without /ToUnicode whose glyph names match their codes (A_glyph at A) while each glyph draws another letter. The font metadata is consistent, so default conversion still leaks it. Like EG_001, --verify now quarantines the disputed line instead of leaving it in the body. The rendered word is not recovered; OCR supplies no confidence scores.
- EG_019, EG_020: flagged. The composite font lacks its /Subtype (EG_019 on the Type 0 font, EG_020 on the CIDFont), so pdfjs cannot load it and has no letters for the text. The hidden block says `unreadable font text: (letters not decodable)`; the visible word is not recovered.
- EG_021, EG_022, EG_023, EG_025: flagged. A composite font with no /ToUnicode and no font program in the file (descriptor, /CIDSystemInfo or /Type removed): its two-byte codes map to nothing, and the text layer holds the codes themselves as CJK characters. That text goes under `unreadable font`; the visible word is not recovered.

The current run signals 24 pages in 9 files; the documented previous rate was 24 of 1,409 pages in 9 of 39 files. The comparison threshold is unchanged. The new action keeps whole lines containing the disputed words under `text not drawn as written`, including short words on those lines. Remaining lines stay. These clean moves include equations, chart labels, protein sequences and accented affiliations; the kind records OCR disagreement and can include ordinary text. Full evidence and per-file moves are in `$SEENLINE_BENCH_CACHE/verify-cost.json`, written by the verify benchmark command.

Rendered text is not substituted: the callback supplies no confidence scores. Existing comparison limits remain: near matches, short or numeric text, non-Latin words, word sets that lose reading order, and recognition omissions can hide a substitution. Pages over the comparison budget keep a notice and their text; no disputed lines can be identified there.
